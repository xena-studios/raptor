# Databases

Managed SQL databases on owners' own nodes, with a browser for them in the app: MariaDB, MySQL, and PostgreSQL first, then Redis (and Valkey, its BSD fork) and MongoDB. Included in the node's price, never hosted by Raptor (DECISIONS #296–#299). They run on the node's [networks](NETWORKS.md), built first. Phases 1 (instances and databases), 2 (the browser), and 3 (import, export, and read-only users) are built; the rest is the plan ([ROADMAP.md](ROADMAP.md#networks-and-databases), DECISIONS #305–#308).

## How phase 1 is built

- `internal/wings/databases`: instances in `database_instances` (engine, version line, image digest, sealed root password, networks, limits, settings), databases in `databases`, instances' fixed addresses in `instance_addresses`. A server's databases have no foreign key to `servers`: they're dropped on their instance first, when the server is deleted (`ServerDeleted`) or at the next start, then removed.
- **Containers** are services (`EnsureService`): created from the spec, created again when its hash (label `raptor.wings.spec`) changes, restarted by Docker (`unless-stopped`), role `database`, a read-only root with `/tmp` in memory, Docker's default seccomp profile, and the memory and CPU limits. Files are in `<volumes>/databases/<id>/{data,run,conf}` on the server data volume, under their own quota project (from the servers' sequence).
- **Wings reaches an instance only through its socket** in `run/`, never the network. MariaDB and MySQL's root is `localhost` only (`*_ROOT_HOST=localhost`); PostgreSQL's `pg_hba.conf` (Wings', in `conf/`, read-only to the engine) is `local all all scram-sha-256`, `host all postgres all reject`, `host sameuser all all scram-sha-256`: a database and its user share a name, so a user can only ever connect to its own database.
- **Names:** a database and its user are `s<the server's short ID>_<name>`, where the short ID is the last 12 characters of its ID (as the app shows it) and the name is up to 18 characters, inside MySQL's 32-character user names. The instance is `<name>.db.raptor` and `<short id>.db.raptor` on its networks.
- **Passwords** are 32 letters and digits, sealed with AES-256-GCM under the node's database key (`databases.key` beside `state.db`, root only).
- **The guard** (`firewall.Guard`): on each of the owner's networks, the instance's fixed address drops connections from any address but the fixed addresses of servers with a database on it, and its IPv6 address (Docker's) refuses them all so clients fall back to IPv4 at once. It's in `forward` before the jumps between networks, so a rule between networks can't reach an instance either; it needs `br_netfilter` with `bridge-nf-call-iptables` on, which Docker sets and Wings makes sure of. On the default network there's no guard: every server there reaches the instance, and only users keep databases apart.
- **Tuning:** the buffer pool or shared buffers from the memory limit (half for InnoDB, a quarter for PostgreSQL), `max_connections` (100), `utf8mb4` with `utf8mb4_unicode_ci`, the performance schema off under 1 GiB (it alone takes hundreds of MB on MySQL), `secure-file-priv=NULL` on MySQL, and the time zone (the node's by default). Advanced settings can change any of these but the fields' (below).
- **Commands:** `node.db.instances` (a read, with the versions), `node.db.usage` (a read; [Health and alerts](#health-and-alerts)), `node.db.instance.save`, `node.db.instance.power`, `node.db.instance.delete` (signed), and for a server `db.list`, `db.create` (returns the password once), `db.delete` (signed), `db.password` (signed), `db.password.reset`. Permissions `databases.read` and `databases.write` (which includes it); the node's are admin-only. Capability `databases`.
- **Tested** against the real engines (`internal/wings/databases`, e2e): each engine starts, a user reaches its own database over the network and not another server's, root can't log in over the network with its password, a new password replaces the old, a restart keeps the data, and a deleted database's user is gone. `TestRuntimeDatabaseGuard` checks the guard: a server with a database reaches its instance, another on the same network doesn't, and the machine always does.

## The model

- **Instance:** one database server on a node, run by Wings as a container: an engine (`mariadb`, `mysql`, `postgres`, `redis`, `valkey`, `mongodb`), a version, a name ("Network A MariaDB"), its limits (memory, CPU, disk), its settings, and who may use it. A node can have **any number**, of any engines and versions side by side.
- **Database:** one database on an instance, for one server, with its own user. A server can have several, on several instances.
- **Networks:** an instance joins one or more of the node's [networks](NETWORKS.md), and only servers on those networks can have databases on it or reach it. This is how two communities on one node are kept apart: each gets its own network and its own instance on it.

Instances aren't eggs or servers: they don't show in the server list, and their lifecycle (create, upgrade, delete) is Wings' own, with the same jobs, backups, and disk limits as servers.

## Isolation

Three layers, so one failing still leaves the others:

1. **Separate instances.** Data that must stay apart goes on separate instances. Nothing in Raptor puts two groups' databases on one instance unless an owner allows both groups' servers on it.
2. **Separate networks.** An instance is reachable only on the [networks](NETWORKS.md) it's joined to, and networks don't reach each other unless an owner adds a rule. Inside a network, the instance's address answers only from servers with a database on it (Raptor's firewall drops the rest), so a server that shares a network but has no database there still can't connect.
3. **Separate users.** Every database has its own user with rights to that database only:
   - MariaDB and MySQL: `GRANT ALL ON db.* TO 'u'@'%'`, nothing global, no `GRANT OPTION`, no `FILE` or `SUPER`; the root password stays on the node and is never given out.
   - PostgreSQL: the database is owned by its user; `REVOKE CONNECT ON DATABASE … FROM PUBLIC`; the `public` schema's create right revoked from `PUBLIC`; `pg_hba.conf` lets each user reach only its own database (`host db u … scram-sha-256`).


Separating game servers themselves (so one community's servers can't reach another's either) is the same networks: see [NETWORKS.md](NETWORKS.md).

## Engines and versions

| Engine | Versions offered | Image |
|---|---|---|
| MariaDB | 10.6, 10.11, 11.4, 11.8 (the LTS releases still supported) | `mariadb:<version>` |
| MySQL | 8.0, 8.4 | `mysql:<version>` |
| PostgreSQL | 14, 15, 16, 17, 18 | `postgres:<version>` |
| Redis | 7.2, 7.4, 8.2, 8.10 | `redis:<version>` |
| Valkey | 8.0, 8.1, 9.0, 9.1 | `valkey/valkey:<version>` |
| MongoDB | 7.0, 8.0, 9.0 (its majors; the x.1–x.3 rapid releases aren't for production) | `mongo:<version>` |

MongoDB 8.0 and later don't start on Linux 6.19 and newer (their memory allocator breaks the kernel's rseq rules, and they exit on purpose: MongoDB's SERVER-121912, unfixed as of October 2026). On such a node Wings marks them unavailable with the reason, MongoDB's default there is 7.0, and creating one or changing to one is refused (DECISIONS #323). The app says why.

The list is in the Wings binary (`internal/wings/databases/versions.go`), each version pinned to an image digest that's updated with Wings releases, so a version means the same bits on every node. An instance tracks a **version line** (11.4), not a patch: Wings moves it to the newest patch in its line when an update brings one, by restarting the container on the new image, at the time the owner picks for maintenance.

### Changing an instance's version

From the instance's menu on the node's Databases page, **Change version** offers the newer versions of its engine. It has to be running: Wings counts every table's rows in every database first. Then:

- **In place** (a newer patch, a newer MariaDB, MySQL 8.0 → 8.4): Wings stops the instance, copies its data, starts the new image on the data, and upgrades MariaDB's system tables (`mariadb-upgrade`; MySQL upgrades itself on start).
- **A new PostgreSQL major** (16 → 17), whose data files don't carry over: Wings dumps every database as the superuser, with owners and rights, stops the instance, puts its data aside, starts the new version on an empty data folder, makes each database, its user, and its read-only user again as they were, and restores each dump into its database in one transaction that stops at the first error (DECISIONS #313).

Either way the rows are counted again, and if the new version doesn't start, an upgrade step fails, or any table has different rows, the old data and version are put back by themselves and the app says why. A change Wings' own stop interrupts is put back at its next start.

The data from before is kept for **7 days** in the instance's folder (so under its disk limit, if it has one; DECISIONS #312), and **Go back** (signed with a passkey) puts it and the old version back; what was written since is lost, and the app says so. After the 7 days, or after another change, there's no going down a version: older engines can't read newer data. The app doesn't offer older versions.

Each change is a job (`db.instance.version`, `db.instance.goback`, one at a time per node), with its step shown on the instance ("Copying its data", "Checking every database"). Servers using the instance lose their connection while it switches, usually under a minute; nothing else can change the instance until it's done.

**Patch updates:** each version line is pinned to an image digest in the Wings binary, so a Wings update can bring a newer patch. The instance then shows **Update available**, and is updated the same way at the start of its maintenance window (04:00 in the node's time unless set; or only by hand), once a day at most, and not while it can still go back (a patch would replace the data kept for that; DECISIONS #315). **Update to the newest patch** does it at once.

### Settings

Each instance has:

- **Limits:** memory (required, and used to size the engine's caches), CPU, and disk, the disk enforced by an XFS project quota like a server's.
- **Tuning:** the settings owners change most, as fields: max connections, the buffer pool or shared buffers (sized from the memory limit unless set), slow-query logging, the character set and collation (MariaDB/MySQL), and time zone.
- **Advanced:** any other engine setting as `name = value` lines, checked against a list of what's safe to set (no file paths, no plugins that load code, no turning off authentication); see [Advanced settings](#advanced-settings).
- **Maintenance window:** when patch updates and planned restarts may happen.
- **External access:** off by default; see [External access](#external-access).

### Advanced settings

**Engine settings** under the instance's Advanced (Wings with capability `db-settings`) takes one `name = value` per line; blank lines and `#` notes are skipped, a value may be quoted, and names take `-` or `_` either way. Each engine has a list of what may be set (`internal/wings/databases/settings.go`), each with its kind and bounds: a whole number or a number within bounds, on or off, one of a few words (`maxmemory-policy`), a list of them (`sql_mode`), a size in the engine's units (`64M`, `64MB`, `64mb`), or a PostgreSQL time with its unit (`30s`). Memory pools (the buffer pool, `shared_buffers`, `work_mem`, `tmp_table_size`) can't be set above the memory limit. A value can only have letters, digits, and `. , _ - + $`, so nothing in one can name a path or carry another option in.

- **Not on any list:** anything naming a file or folder (`datadir`, `*_file`, `dir`, `hba_file`), loading code (`plugin_load`, `shared_preload_libraries`, `loadmodule`), commands the engine runs (`archive_command`), authentication and TLS (`skip_grant_tables`, `password_encryption`, `requirepass`, `ssl`), where it listens (`bind_address`, `listen_addresses`, `port`), replication, `local_infile`, statement logs that write every query (`general_log`, `log_statement`), and what Wings sets for itself (`secure_file_priv`, `skip_name_resolve`, the socket, `aclfile`, `protected-mode`). Max connections and the time zone are fields, so their settings point there.
- **MariaDB and MySQL:** InnoDB's buffer pool, log, I/O and lock settings; packet size and timeouts; table and thread caches; temporary-table and per-query buffers; the slow query log (`slow_query_log`, `long_query_time`; it's a file in the data folder, under the disk limit); `sql_mode`, the character set and collation, transaction isolation, the event scheduler, and the performance schema. MariaDB adds the query cache and Aria's page cache; MySQL its redo log capacity and how long binary logs are kept.
- **PostgreSQL:** memory (`shared_buffers`, `work_mem`, `maintenance_work_mem`, `effective_cache_size`), the planner's costs, WAL sizes and checkpoints, `synchronous_commit`, statement, lock, and idle timeouts, slow statements and lock waits in its log (`log_min_duration_statement`), autovacuum's thresholds, parallel workers, JIT, and lock and prepared-transaction limits.
- **Redis:** the eviction policy (`maxmemory-policy`; writes still fail at the limit unless it's changed), keyspace notifications, timeouts and keepalives, `hz`, the slow log and latency monitor, lazy freeing, the append-only log's fsync and rewrites, active defragmentation, the small-encoding thresholds, LFU tuning, and I/O threads.
- **MongoDB has none**, on purpose: its options are YAML and server parameters, few are both safe and worth having, and nobody has asked. It's a list away when someone does.

They go on the engine's **command line**, after Wings' own (`--name=value`, `-c name=value`, `--name value`), and replace Wings' own for the same setting, so the buffer pool or eviction policy can be set over what Wings derives. Not a config file: PostgreSQL can't include one from its command line (its `postgresql.conf` is in the data folder its image makes), and a container is made again whenever its command changes, so a change takes effect exactly when the instance restarts for it, with nothing left behind. Saving them is `node.db.instance.save` like the other settings (admins).

Wings checks them when they're saved (the authority: a line off the list, out of bounds, or set twice is refused with its line number), and again at each start, where a line a newer Wings no longer allows is left out rather than keep the instance from starting. The app checks them as they're typed with the same rules, from `web/src/lib/db-advanced.json`, which `TestAdvancedRulesForWeb` keeps equal to Wings' (`go test ./internal/wings/databases -run TestAdvancedRulesForWeb -update` writes it); both run the cases in `testdata/advanced_cases.json`, and `FuzzParseAdvanced` checks nothing it accepts is off the list or unsafe on a command line.

Wings' own sessions never land in a statement log advanced settings turn on, as its statements carry users' passwords: its MariaDB and MySQL connections set `long_query_time` to a year, and its PostgreSQL ones (and `pg_dump` and `psql` as the superuser) `log_min_duration_statement=-1` and `log_statement=none`.

`TestAdvancedSettings` (e2e) sets some on each engine, reads them back from the running engine, changes them, and checks a line off the list is refused.

## External access

From the instance's menu, **External access** (admins, signed with a passkey, since it opens a port) gives an instance a port on the node, for a desktop tool or an app somewhere else:

- **A port** from 1024 to 65535 that isn't Wings' own, a server's allocation, another instance's, or bound on the machine (and servers can't be given it after). Docker publishes it on every address the node has, IPv4 and IPv6.
- **An allowlist** of addresses and ranges, at least one (32 at most). The firewall drops connections to the port from anything else before Docker forwards them, the node's own containers included, so it can't become a way between networks (DECISIONS #316). `0.0.0.0/0` is accepted, with a warning in the app.
- **TLS, required from outside.** Wings makes a certificate authority for the instance and a certificate naming the node's DNS name (`<short id>.raptornodes.net`) and the instance's host names; the app offers the authority's certificate, so tools can check it (`sslmode=verify-full` with `sslrootcert`, or `--ssl-ca` with `--ssl-mode=VERIFY_IDENTITY`). Servers on the instance's networks keep connecting without TLS, as many plugins can't do it (DECISIONS #317): PostgreSQL requires it in `pg_hba.conf` for every address but its networks'; MariaDB and MySQL give each user an account per network that requires nothing, beside the one for everywhere else that requires TLS. The networks' gateways count as outside: with Docker's userland proxy on, outside connections arrive from there.
- **The same users:** each database's own user and its read-only user, which reach only their database. The instance's administrator never logs in over the network (on SQL engines; Redis' and Valkey's can, with its 32-character password: DECISIONS #320, accepted in #332).
- **Redis and Valkey** (DECISIONS #331): Redis can't require TLS from some clients and not others on one port, so a second port in the container (6380) speaks only TLS (`--tls-port`, the instance's certificate, clients not asked for one), and only it is published; the plain port (6379) stays on the instance's networks, where plugins keep using it. Clients connect with `rediss://` or `redis-cli --tls --cacert`. Capability `db-redis-external`.
- **MongoDB has none**, on purpose (#331): its TLS mode is per port and all or nothing, and it has no second port, so outside connections with TLS would mean every plugin inside speaking TLS too. It waits until someone asks; Wings refuses it with the reason.

Turning it on, changing it, or turning it off restarts the instance. Each database's row on the server's Databases tab shows the address from outside and the certificate.

## Using a database from a server

Creating a database on a server's **Databases** tab gives it:

- a name (`s<short id>_<name>`, the server's short ID being the last part of its ID), a user with the same name, and a random password, made on the node;
- connection details in the tab, and as **environment variables** for the server's next start: for its first SQL database `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, and `DATABASE_URL` (`mysql://…` or `postgres://…`); for its first Redis one `REDIS_HOST`, `REDIS_PORT`, `REDIS_USER`, `REDIS_PASSWORD`, and `REDIS_URL`; for its first MongoDB one `MONGODB_HOST`, `MONGODB_PORT`, `MONGODB_DATABASE`, `MONGODB_USER`, `MONGODB_PASSWORD`, and `MONGODB_URI` (with `authSource`); with more than one database, each also gets its own with its name as a prefix (`LUCKPERMS_DB_HOST`, `CACHE_REDIS_URL`…);
- a host name that resolves on the instance's networks, `<instance name>.db.raptor`, so configs don't hold an IP that could change.

The password lives on the node (encrypted in `state.db`), never in the Panel. The tab shows it once when the database is made; after that, **Show password** fetches it from the node with a re-auth, and **Reset password** makes a new one.

## Redis and MongoDB

- **Redis** has no isolation between databases worth the name (its databases are numbers, and limiting a user to keys with a prefix only works if every plugin prefixes its keys), so **a Redis instance holds one server's data**: Wings refuses a second server's database on it. Make one per server; they're small (256 MB is plenty for a cache). The server's user is an ACL user that can run everything but administration (`CONFIG`, `MODULE`, `DEBUG`, `SHUTDOWN`, replication) and the dangerous commands other than the few apps use (`FLUSHDB`, `FLUSHALL`, `KEYS`, `INFO`, `SORT`); the read-only user reads. The `default` user is off. Data is kept with Redis' append-only log, and writes fail when the memory limit is reached rather than keys being dropped.
- **MongoDB** instances are shared like the SQL engines': each database has its own user, stored in that database (its `authSource`) with `readWrite` on it alone, and its read-only user `read`. MongoDB 8.0 and later need a CPU from about 2016 on (ARMv8.2 or x86 with AVX); 7.0 runs on older ones.
- Both get read-only users, backups (a Redis snapshot or a `mongodump` archive), restoring one database from a backup, and version changes in place; MongoDB also imports and exports `mongodump` archives (`.archive.gz`) through the server's files (in Wings; the app's buttons come with the document browser, which they live in). Redis has no imports or exports: its data is in the server's backups.
- External access: Redis on a second, TLS-only port; MongoDB none, on purpose ([External access](#external-access), DECISIONS #331).
- **Valkey** (DECISIONS #333), the BSD-licensed fork of Redis 7.2 that Linux distributions and clouds moved to, is an engine of its own beside Redis: the same protocol, commands, ACL file, snapshots, and append-only log, so a plugin that takes Redis takes it unchanged, and everything above is the same for it (one server's data, the key browser, `REDIS_*` variables, backups, version changes, external access, advanced settings). It runs `valkey-server` from the official `valkey/valkey` images, as uid 999 like Redis. Moving an instance between Redis and Valkey isn't offered; a new instance and the server's backup restored into it does it.

### The key and document browsers

**Open** on a Redis, Valkey, or MongoDB database opens its own browser, as the database's own user through the instance's socket, like the SQL browser:

- **Redis:** keys found by a pattern (`player:*`, `SCAN`, a page at a time), each with its type and time to live; a key's value by type: a string (the editor, as JSON when it is; RedisJSON documents too), a hash's fields, a list, a set, a sorted set's members and scores, a stream's latest entries; with **Change databases**, setting a string, adding, changing, and removing fields and members, renaming, the expiry, deleting, and new keys. Keys that aren't UTF-8 travel as hex. **Command** runs any command, like `redis-cli`, as the database's user (which can't run administration); those who may only look run only commands Redis itself flags read-only, and commands that would hold the connection (`BLPOP`, `SUBSCRIBE`, `MONITOR`, `MULTI`) don't run at all (DECISIONS #322).
- **MongoDB:** the collections with their counts and indexes; a collection's documents found with a filter and sorted (both JSON, MongoDB's query language), 50 to a page, as relaxed Extended JSON (`{"$oid": …}`, `{"$date": …}`), so editing one and saving it changes only what was edited; with **Change databases**, inserting, editing (the `_id` stays), and deleting documents, and making and dropping collections. **Import** and **Export** move `mongodump` archives through the server's files.
- Changes are recorded like the SQL browser's, with how many keys or documents they changed and never their content.

### How phase 6 is built (instances and databases)

- Migration `00025` rebuilds `database_instances` to allow `redis` and `mongodb` (SQLite can't change a CHECK constraint), with `databases` and `instance_addresses` rebuilt alongside so its cascades never fire; `TestDatabaseEnginesMigration` checks nothing is lost and the references still cascade.
- `redis.go`: the container (as uid 999 from the start: Redis 8.4's entrypoint drops root with `setpriv`, which needs a capability database containers don't get; `ServiceSpec.User`, left out of the spec's hash when empty), its ACL file in the data folder (written once with Wings' user, then kept by Redis with `ACL SAVE`), users through `ACL SETUSER`/`DELUSER` over the socket. Backups are a `BGSAVE`'s snapshot read from the data folder; restoring one stops the instance and makes the snapshot the base of a new append-only log (with it on, Redis 7+ loads only the log), then starts it.
- `keys.go` (the key browser: `db.keys`, `db.key`, `db.key.edit`, `db.redis.command` and `.read`) and `documents.go` (the document browser: `db.collections`, `db.documents`, `db.document.edit`, `db.collection.edit`), with permissions like the SQL browser's and capability `db-documents`. A command's `id` is the database's, so a document's is `doc_id` (`TestBrowserParamsDecode` checks no embedded field shares a name with it). `TestKeyBrowser` and `TestDocumentBrowser` cover every type, binary keys, the read-only rule for commands, what's refused, Extended JSON both ways, replacing by an ObjectId and by a number, and paging.
- `unixsock.go`: instances' sockets are dialled through their folder's descriptor (`/proc/self/fd/<n>/<name>`) when their path is over the kernel's 108 bytes, which a volume at a long path (or a test's temporary folder) makes it.
- `mongo.go`: the container (the image's entrypoint makes Wings' root user), `createUser`/`updateUser`/`dropUser` over the socket, `mongodump` and `mongorestore` run in the container as the database's user with the password in a config file on its `/tmp` (a tmpfs), written through stdin and removed after. Restores map any source database onto the target (`--nsFrom=$db$.$coll$`) and leave out `admin`, `config`, and `local`. A version change raises the feature compatibility version (`setFeatureCompatibilityVersion`, with `confirm`) once the new version runs, and goes one major at a time.
- The engines plug into the existing functions at the top (`createDatabase`, `dropDatabase`, `setPassword`, `grantReadOnly`, `dropReadOnly`, `ping`, `dumpTo`, `importFrom`, `inventory`); the SQL browser and external access refuse them.
- Migration `00028` rebuilds the same tables again to allow `valkey` (`TestValkeyMigration`); `isRedis` is where the code treats the two alike.
- **Tested** (`TestRedis`, for Redis and Valkey, `TestRedisExternal`, `TestMongoDB`, real engines): Redis' user does what apps do and no administration, the `default` user is off, a second server's database is refused, the read-only user reads only, a new password replaces the old, a snapshot restores over later changes, 8.2 → 8.10 keeps the keys, and deleting the database drops its user and data. MongoDB's users reach their own database only, not another server's or `admin`'s users; the read-only user reads only; an export imports back; a backup's dump restores; 7.0 → 9.0 is refused and 7.0 → 8.0 keeps the data and raises the feature compatibility version; deleting the database drops it and its users. On the dev node, a server got its `REDIS_*` and `MONGODB_*` variables and reached both instances, and a container that wasn't a server with a database there couldn't.

## The browser

### How phase 2 is built

- `internal/wings/databases/browser.go`: every command opens a connection **as the database's own user**, through the instance's socket, with its sealed password, so nothing in the browser reaches further than that user can. Table and column names from the app are only used once found in the live schema, then quoted; values are always parameters (PostgreSQL's sent as literals the engine casts to the column's type, so a string can go into any column).
- **Rows** are paged by `LIMIT`/`OFFSET` (one more than asked, to know there's more), ordered by the primary key unless sorted, with filters (`=`, `<>`, `<`, `<=`, `>`, `>=`, contains, NULL, not NULL); row counts are the engine's estimates. **Edits** go by the whole primary key in one transaction, and an update or delete that doesn't match exactly the rows asked for changes nothing; a table without a primary key is read-only in the grid. Values over 8 KB arrive cut and can't be edited in the grid.
- **Queries:** those with **Change databases** run any SQL (`db.query`): on PostgreSQL every statement's result is read and the last shown, with its rows changed; on MariaDB and MySQL statements that return rows (by their first word) are read and the rest executed, the last one's count shown. Those with only **See databases** run `db.query.read`: **one statement** (MariaDB and MySQL's connection takes no more; PostgreSQL's extended protocol neither), in a **read-only transaction**, MariaDB and MySQL's session read-only too, rolled back after, and **as the database's reader**, a user that can only read (DECISIONS #329, below). The e2e test tries `DELETE`, `DROP`, `CREATE`, `UPDATE`, and a second statement after a `SELECT` or a `COMMIT` on every engine; all fail.
- **Limits:** the SQL editor's results stream (below): up to 10,000 rows and 32 MB of a result are shown and the rest counted, a value at most 8 KB shown, and a query runs for 30 seconds by default and at most 10 minutes. A query past its limit, cancelled, or whose stream closed is stopped on the server (MariaDB and MySQL's `KILL QUERY` as root, PostgreSQL's `pg_cancel_backend` and `statement_timeout`). `db.query` without `stream` (the structure forms, and Panels' fallback) still answers in one message: 1,000 rows and 2 MB, 50 seconds.
- **Structure** forms (create table with an auto-numbered `id`, add and drop columns, add and drop indexes, rename and drop a table) write the SQL in the app, show it, and run it as `db.query`.
- **Processes** are the connections the database's user can see (its own), with their running query, and stopping one (`KILL QUERY`, `pg_cancel_backend`).
- **Activity:** `db.query`, the row edits, and stopping a query are recorded like any change, with `rows_changed` from their result and never their SQL (the Panel doesn't keep commands' params). Reads aren't recorded.
- Commands: `db.schema`, `db.rows`, `db.query.read`, `db.processes`, `db.query.cancel` (See databases), `db.query`, `db.row.insert`, `db.row.update`, `db.row.delete`, `db.process.kill` (Change databases); none signed. Capability `db-browser`.

### How streamed queries, readers, and the instance page are built

- **Streamed queries** (`stream.go`) travel like the file manager's downloads (DECISIONS #311): `db.query` or `db.query.read` with `stream` checks the SQL, opens the session, and answers a query ID at once; the Panel's `POST /api/databases/query` (`internal/panel/transfers/query.go`) runs that command as the user, opens a transfer connection for the ID, and copies what Wings' `GET /query` on it sends (`internal/wings/link`) to the browser line by line: `{"query_id"}` first, then `{"columns"}`, `{"rows"}` in batches of up to 500 rows or 256 KB, `{"wait"}` every 10 seconds while nothing else comes (so proxies keep the response open), and `{"done"}` (statements, rows changed, rows read and shown, whether there were more) or `{"error"}`. A query nobody streams within 30 seconds is closed; a node runs at most 16 at once, 4 per user. Rows past what's shown are read and counted, not kept, so statements after a big `SELECT` still run.
- **Cancel:** `db.query.cancel` (the user who started it only) or the stream closing ends the query's context, and `run` stops it on the engine as root, on every engine (a cancelled MariaDB or MySQL `SLEEP` returns early without an error, so a run whose context ended is reported stopped either way). Redis and MongoDB have no long queries from the browser: their commands answer in one message, within a command's minute.
- **The activity:** the Panel records the command once the stream ends (`commands.ExecuteThenRecord`), with `rows_changed` from its `done`, never its SQL. A node from before streaming answers `stream` with a whole result, which the Panel sends as lines too. The web app streams only on nodes with capability `db-query-stream`.
- **The whole result:** `db.export` with `query` (`ExportQuery`) writes a query's every row as CSV to `database-exports/<name>-query-<time>.csv`, as a job like any export, running the SQL like a reader's: one statement, read-only, as the database's reader, so a `DELETE` there fails and changes nothing.
- **Readers** (`viewer.go`): a SQL database's reader is `v<short id>_<name>`, made with `grantReader` (`grantReadOnly`'s rights) the first time a reader needs it, its sealed password in `databases.viewer_password` (migration `00027`). It only logs in through the socket: MariaDB and MySQL's account is `'v…'@'localhost'` (which `syncAccounts` leaves alone), and PostgreSQL's `pg_hba.conf` matches it only on `local`. A login it's refused (dropped by hand, or a restore that didn't carry it) makes it again, once; `provision` gives it its rights back after a database is made again; deleting the database drops it. It's never shown: not in connection details, nor the instance's users.
- **The instance page** (`instance.go`, DECISIONS #330): `node.db.databases` (the instance's databases, of every server), `node.db.users` (its users from `mysql.user` and `mysql.db`, or `pg_roles` and `has_database_privilege`, each with what it is to Raptor and what it reaches), `node.db.processes` and `node.db.process.kill` (every connection, as root); admins only, unsigned, capability `db-instance-browser`. A database opened there is the server's own browser, through the server's commands (admins have Change databases on every server), so nothing on the page runs SQL as the administrator.
- **Tested** (`testReader`, `testStream`, `testInstancePage` in `TestEngines`, real engines): a reader's query runs as `v…` and a writer's as the database's user; the reader can't insert, drop, or create outside a transaction, can't log in over the network, and is made again when dropped; a 10,005-row result shows 10,000 and counts 10,005; an update's stream says it changed 2 rows; a 60-second sleep is stopped within seconds by `db.query.cancel` (as a reader and a writer), by its stream closing, and by an admin's `node.db.process.kill`, and is gone from the engine after, while another user's cancel is refused; the instance's users list each database's user and read-only user with what they reach, the administrator with everything, and no reader. `TestTransfers` exports a query's result as CSV, and an export of a `DELETE` fails and changes nothing. `TestQueryStream` (the Panel, with a real node link) checks the lines, the activity's `rows_changed`, the permissions, an old node's whole result, and that closing the response stops the query on the node.

### How phase 3 is built

- **Through the server's files**, which already move big files both ways (DECISIONS #311): an import runs a `.sql` or `.sql.gz` file the server has (gzip known by its first bytes); an export writes `database-exports/<name>[-<table>]-<UTC time>.sql.gz` (or `.csv`) into the server's files, through a `.part` file renamed when it's done, for the file manager to download. Both are jobs (`db.import`, `db.export`, in the files class), followed with `db.transfer.status` (bytes so far, of how many for an import) and stopped with `db.transfer.cancel`.
- **The engines' own tools**, run in the instance's container as uid 999 with Docker's exec (`Runtime.Exec`), their input and output streamed: nothing is written in the container, and the password goes in the environment (`MYSQL_PWD`, `PGPASSWORD`), never on a command line. As the database's own user, through the socket:
  - MariaDB/MySQL: `mariadb`/`mysql --binary-mode` to import, stopping at the first error; `mariadb-dump`/`mysqldump --single-transaction --no-tablespaces --skip-lock-tables --triggers` (MySQL also `--set-gtid-purged=OFF`) to export, consistent without locks and needing no rights the user lacks.
  - PostgreSQL: `psql --set=ON_ERROR_STOP=1` to import; `pg_dump --no-owner --no-privileges` (with `--table` for one) to export.
  - A failure's error is the tool's line that names it (psql's, not the `^` under it).
- **CSV** of a table is written by Wings itself, streamed row by row through the browser's connection; a query result's CSV is made in the app from the rows on screen, or written by Wings with every row (`db.export` with `query`, below).
- **Read-only users:** `r<short id>_<name>` beside `s<short id>_<name>`, made on request (`db.readonly.set`, which gives an existing one a new password), with `SELECT` and `SHOW VIEW` on the database (MariaDB/MySQL), or on PostgreSQL `CONNECT`, `USAGE` and `SELECT` on every schema, its tables and sequences, and the database user's default privileges so tables made later are readable too. PostgreSQL's `pg_hba.conf` gets a line per read-only user for its own database, and is reloaded; removing one (`db.readonly.remove`) drops what it was granted (`DROP OWNED BY`) and the role. Deleting a database removes its read-only user. The password is shown with a passkey, like the database's (`db.password` with `readonly`).
- Importing changes data and exporting gives it out, so both, and read-only users, need **Change databases**. Capability `db-transfers`.
- **Tested** (`TestTransfers`, real engines): a database exported and imported back, a table as CSV (quotes and commas), a broken file failing with the engine's reason, and a read-only user reading tables made before and after it, failing to insert or drop, gone once removed, and gone with its database.
- **Imports from elsewhere:** a dump that makes or switches databases (`CREATE DATABASE`, `USE`), sets owners (`ALTER … OWNER TO`), or has `DEFINER` clauses needs rights the database's user doesn't have, and stops there. Export with `--no-owner` (PostgreSQL) or without those (MariaDB/MySQL).

## Permissions

- **See databases:** the Databases tab, connection details (without the password), the schema, rows, and read-only queries, which run as the database's **reader**: a read-only user Wings makes for the browser the first time it's needed, which logs in only through the instance's socket and is never shown (DECISIONS #329).
- **Change databases:** everything in the browser: editing rows, any SQL, structure, imports and exports, read-only users, and showing or resetting the password.
- Admins and owners: creating and deleting instances, changing their versions and settings, external access, and which servers may use them; creating databases for any server; an instance's own page.
- **Signed with a passkey:** deleting a database or an instance, restoring a database over itself, going back to an instance's version before a change, and turning on external access (it opens a port).

## Backups

- **A server's backups hold its databases** (DECISIONS #314): after the egg's pre-backup commands, Wings dumps each one as its own user (plain SQL, like an export: `--single-transaction` on MariaDB and MySQL, so it's consistent without locks) into a folder outside the server's files, which the snapshot adds at the top as `.raptor-databases/<name>.sql`. The dumps never use the server's disk or count against its limit, and the server's ignore rules don't apply to them. A database whose instance isn't running is left out with a warning on the backup; the files are backed up anyway. The backup list says which databases each backup holds.
- **Restore everything** restores them too, before the server starts: each database is emptied (dropped and made again, with its user, password, and read-only user kept) and its dump run into it. A dump of a database the server doesn't have any more is left in `.raptor-databases` for importing by hand. The safety backup taken before a restore holds the databases as they were, so the restore can be undone. Backups from before this version of Wings hold no databases, and restoring one leaves the databases as they are.
- **One database alone:** the database's **Restore from a backup** (signed) lists the backups that hold it. Wings exports what the database has now to `database-exports/<name>-before-restore-<time>.sql.gz`, takes the dump out of the backup, and restores it the same way, leaving the server's files alone (`db.restore`, followed with `db.transfer.status`).
- Instances aren't backed up on their own: every database belongs to a server, whose backups cover it.
- A version change keeps the data from before it (above).

### How phase 4 is built

- `internal/wings/databases/upgrade.go`: `ChangeVersion` and `GoBack` queue jobs in the `database` class (one at a time per node), each holding the instance's lock throughout; while one is queued or running, everything else that changes the instance answers that it's changing version. `migrates` decides in place or by migration from the version numbers, and refuses going down.
- The change: `inventory` counts every table's rows as root through the socket; the data is copied into `previous/data` with `copyTree` (through `os.Root` on both sides, since the engine can write in the data folder; `copy_file_range` reflinks on XFS) or, for a PostgreSQL major, dumped to `previous/dumps` with `pg_dump` as `postgres` and renamed aside. A marker in `previous/` records the instance's row from before, and whether its data was switched yet, so `recover` at Wings' start puts an interrupted change back. Then `SetInstanceVersion`, `ensureLocked` on the new image, `mariadb-upgrade` for MariaDB, the restores for PostgreSQL (`provision` makes each database, user, and read-only user from `state.db`, then `psql --single-transaction --set=ON_ERROR_STOP=1`), and the count again; any error runs `putBack`.
- State: `database_instances` gained `prev_version`, `prev_image`, `rollback_until`, and `patch_tried` (migration `00023`). The instance reports `update` (its image isn't this Wings' digest for its line), `previous` and `go_back_until`, and `change` (the job, its step, and how it ended, kept in memory).
- `housekeeping` runs every minute: it removes kept data past `rollback_until`, and queues a patch for instances on an older digest at the hour of their maintenance window (`settings.maintenance`, `HH:00`, `off`, or 04:00 by default), in the node's time zone.
- `internal/wings/databases/backups.go`: `Dump` and `Restore` implement the backup manager's `Databases`; `RestoreDatabase` is `db.restore`'s job. Restores open the folder through `os.Root` without following links, since it came from the server's files.
- `internal/wings/backup`: `SnapshotRequest.Extra` adds folders from outside the server's directory at the top of a snapshot; the engine applies the server's ignore rules (and `.pteroignore`) to its own files with Kopia's `ignorefs` first, then joins the extra folders, with the uploader's own ignore pass off. Backups record their databases (`backups.databases`, mirrored to the Panel's `m_backups.databases`). `ExtractDatabase` takes one dump out for `db.restore`.
- Commands: `node.db.instance.version` (admins), `node.db.instance.goback` (admins, signed), `db.restore` (Change databases, signed). Capabilities `db-versions` and `db-backups`.
- **Tested** (`TestVersions`, `TestBackupDumps`, real engines): MariaDB 11.4 → 11.8 and MySQL 8.0 → 8.4 in place and PostgreSQL 16 → 17 by migration, each with its rows, its user and password, and its read-only user (still read-only) carried over, then going back to the data from before; a change to an image that can't start put back with its rows; a patch queued by the maintenance window and applied once; a server's databases dumped, restored over changes made since (a table made after is gone), and one restored alone with what it had exported first. `TestDatabasesInBackups` checks the backup manager records and restores them, takes them into the safety backup, and turns a database it couldn't dump into a warning; `TestExtraFolders` checks no ignore pattern can leave the dumps out.

Each database opens in the server's Databases tab, and an instance's whole contents on its own page (admins). Everything goes through typed commands to Wings (`db.schema`, `db.rows`, `db.query`, `db.row.update`…), which connects to the instance locally as that database's user, or its reader for those who may only look, so the browser can never reach further than the database's own rights. An instance's page sees the instance as a whole as its administrator (its databases, users, and connections) and opens each database in the server's own browser, as that database's user (DECISIONS #330).

- **Schema:** tables, views, and their columns, types, keys, and indexes; each table's row count and size.
- **Rows:** paged (100 at a time, up to 1,000 per page with a setting), sorted, and filtered by column, with JSON and long text opened in the editor. **Edit, insert, and delete** rows in place; a table without a primary key is read-only in the grid (there'd be no safe way to say which row).
- **SQL editor:** the file manager's editor with SQL highlighting and completion from the schema. Results stream into a grid as they're read, 200 rows to a page, with how many rows and how long; a statement that changes data says how many rows it changed. Every statement is allowed, including DDL: the database's user can only touch its own database anyway. Each run has a time limit (30 s by default, up to 10 minutes) and shows up to 10,000 rows, counting the rest; **Cancel** stops it on the engine, and **Export the whole result** writes every row as CSV into the server's files.
- **Structure:** create, alter, and drop tables, columns, and indexes from forms, shown as the SQL they'll run before running it.
- **Users** (instance page): the instance's users and what each can reach, and a read-only user for any of its databases, for an outside tool.
- **Import and export:** upload a `.sql` (or `.sql.gz`) file to run against the database, as a job with progress; download a dump of a database or a table as `.sql`, or a table or a query's whole result as CSV.
- **Processes:** what's connected to the database now (on the instance page, every connection to the instance), and stopping a query.

Results travel through the Panel like the file manager's do (encrypted, not stored). Queries that change something are recorded in the server's activity with who ran them and how many rows they changed, but not their text, which can hold data.

### How phase 5 is built

- `internal/wings/databases/external.go`: `SetExternal` (`node.db.instance.external`, signed, admins) checks the port (`checkPort`: Wings' ports, `allocations`, other instances, a test bind) and the allowlist (`parseAllow`: addresses become /32 or /128, ranges are masked, zones refused), stores them (`external_port`, `external_allow`, migration `00024`), and restarts the instance. The server manager's `checkConflicts` refuses allocations on an instance's port.
- `tls.go`: the authority (P-256, 20 years) with its key at `<instance>/tls-ca.key`, root's alone and outside what the container sees; the server certificate (2 years) in `conf/tls`, its key owned by the engine's user. It's made again at a start when it's within 60 days of expiring or names something else.
- The container: `ServiceSpec.Publish` (left out of the spec's JSON when empty, so instances without external access keep their hash and aren't restarted by the update), `conf` mounted at `/etc/raptor` for MariaDB and MySQL too, and the engine's TLS flags (`--ssl-cert`…, `ssl=on`).
- Who needs TLS: `pgHBA` with the instance's networks (`hostnossl … <gateway>/32 reject`, `host sameuser all <subnet>`, then `hostssl sameuser all all`); `syncAccounts` after every start and every new user, password, or read-only user, which gives each MariaDB or MySQL user exactly `accountHosts`' accounts (`%` requiring SSL, `localhost` for the socket and each network's subnet as address/netmask requiring nothing, each gateway requiring SSL), with its password and rights. Dropping a user or changing its password covers all of its accounts.
- The firewall (`firewall.External`): in `prerouting` at `dstnat - 1`, `fib daddr type local tcp dport <port>` from an address not allowed is dropped, per family; and an instance's network guard lets connections Docker translated through (`ct status dnat accept`) ahead of its drop. Capability `db-external`.
- **Tested** (`TestExternal`, real engines, under Wings' umask): from the node's own address, a user and the read-only user connect with TLS checked against the instance's authority and the host name, and not without TLS; a server's plugin on the network (the engine's own client in a container) connects without TLS; another instance can't take the port; turning it off closes the port and leaves each MariaDB or MySQL user one account. Unit tests cover the allowlist, the accounts, `pg_hba.conf`, the certificates, and the rules; on the dev node, a container off the allowlist timed out on the port and connected once its range was added.

## Health and alerts

- Each instance's state: running, starting, stopped, upgrading, or failed (with why).
- An instance is **running** once it answers on its socket as the real server. On a first start the images' entrypoints run a temporary server on the same socket (MariaDB and MySQL with `skip-networking`, PostgreSQL with no `listen_addresses`) to set the root password; until that one is gone, the instance is still starting, so nothing connects in the gap before the real server opens its socket.
- **The watch** (`internal/wings/databases/health.go`), every 15 seconds, looks at each instance that should be running and isn't being started, changed, or stopped (its lock is free). If its container is gone, stopped, or was restarted by Docker (its restart count went up since it last answered), it's **down**: `db.instance.down` is raised with why, and it's started again, which waits for it to answer and fails it if it keeps stopping. Once it answers again, `db.instance.up`, with how long it was down. Each is raised once however often it restarts, and which instances are down is kept in `state.db` (`databases.down`), so a Wings restart neither repeats the alert nor misses the instance coming back. An instance that fails to start when it should run (at Wings' start, after a change of settings, or started by hand) is down too. One stopped or deleted is forgotten, without an "up".
- **Usage**, sampled by the watch for each running instance: memory (Docker's stats), disk (its quota project, or a scan of its folder every 5 minutes without quotas), connections, uptime, and queries a second, against its limits and max connections. The engine answers the last three in one statement or command on one connection: `SHOW GLOBAL STATUS` (`Threads_connected`, `Uptime`, `Questions`), one `SELECT` on `pg_stat_activity`'s client backends, `pg_postmaster_start_time()`, and `pg_stat_database`'s `xact_commit + xact_rollback`, Redis' `INFO` (`connected_clients`, `uptime_in_seconds`, `total_commands_processed`), or MongoDB's `serverStatus` (`connections`, `uptime`, `opcounters`). Queries a second is the counter's change since the sample before, less what sampling adds to it itself (`ownOps`: its connection's setup, the asking, and closing it, measured on the real engines, so an idle instance reads 0): statements for MySQL and MariaDB, transactions for PostgreSQL, commands for Redis and Valkey, operations for MongoDB. Each engine's own counter is used rather than Redis' `instantaneous_ops_per_sec`, a 1.6-second window that would count Wings' own `INFO`, so all of them are averages over the same 15 seconds. There's none for the first sample, or after the engine restarted (its uptime went down) or its counters were reset. The last 40 samples (10 minutes) are kept in memory for the app's trend. **The app** asks with `node.db.usage` (admins only, unsigned, a read; capability `db-usage`) every 15 seconds, as it does `node.metrics` for a node: each running instance's latest sample and its recent ones. The node's Databases page shows a strip under each running instance (memory and disk of their limits, connections of its max, queries a second, uptime), and its own page a row of stats like a server's, with the trend of its connections and queries. `raptor db ps` shows memory, disk, and connections.
- **Alerts** ([PANEL.md](PANEL.md#alerts)): an instance down or restarting (`db_down`, resolved when it's back), its disk or connections above a percent of its limit for a while (`db_disk_high` and `db_connections_high`, threshold rules evaluated by Wings from the usage), and a version change, patch update, or going back finished or failed (`db_version`, from `db.instance.version` when the job ends). They apply to every node or one, go to owners and admins only (members don't manage instances), and link to the node's Databases page (DECISIONS #328). Capability `db-alerts`: the Panel sends instance threshold rules only to nodes that list it.
- **`raptor doctor`** checks each instance that should run is running, answers on its socket now, and is on each of its networks at its fixed address as Docker has it; and that each of the owner's networks is on Docker with its subnet. **`raptor db ps`** lists the instances: short ID, engine and version, state, memory, disk, connections, databases, and networks. Both ask Wings over its local socket (`ListDatabaseInstances`, `ListNetworks`).
- **Tested:** `TestWatch`, `TestQueryRate` (the rate less Wings' own asking, never below 0, none on the first sample or after a restart or reset), and `TestVersionEvent` (the trend capped at 40 samples, a fake Docker: a restart and a stop each alert once, a Wings restart in between, a container gone, one stopped by hand forgotten), `TestInstanceThresholds`, the Panel's `TestAlerts` (an instance down reaches the owner and not a member a rule names, and instance rules reach only nodes with `db-alerts`), the doctor's checks, and on real engines (`testHealth` in `TestEngines`, `TestRedis`, `TestMongoDB`): usage with the engine's own connection count and an uptime under an hour, queries a second at 0 while only Wings asks and a burst of 200 queries counted as about 200 (`testQueryRate`), the instance answering on its network at its address, and one stopped behind Wings' back down, started again, and back up, one event each.

## Phases

1. **Instances and databases (MariaDB, MySQL, PostgreSQL),** after [networks](NETWORKS.md#phases): creating instances with any version, limits and tuning, on chosen networks; the firewall rule for servers without a database; creating databases and users for servers; connection details, environment variables, and host names; passwords on the node; the Databases tab and the node's Databases page; capability `databases`.
2. **The browser:** schema, rows with editing, the SQL editor, structure forms, processes.
3. **Import, export, and users:** `.sql` imports as jobs, dumps and CSV exports, read-only users.
4. **Versions and backups:** patch updates in the maintenance window, in-place and migration upgrades with rollback, databases in server backups. Built, without instance backups of their own (DECISIONS #314).
5. **External access:** the port, the address allowlist, TLS. Built.
6. **Redis and MongoDB:** one instance per server for Redis (it has no real per-database isolation), shared instances with per-database users for MongoDB; a key browser and a document browser. Built, with Valkey beside Redis (#333) and external access for both on a TLS-only port; MongoDB's stays off (#331).
