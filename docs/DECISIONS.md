# Decisions Log

Locked decisions and the reasons behind them. Change a decision by adding a new entry that supersedes the old one. Don't edit history.

| # | Decision | Why |
|---|---|---|
| 1 | **Product:** hosted panel; owners bring their own Linux boxes | SaaS with no hardware costs. Owners keep control of their machines. |
| 2 | **Audience:** server owners and people with boxes who lack a reliable way to host. **Not** hosting companies. | Hosting companies need white-label, billing integrations, and reseller features. That's a different product. |
| 3 | **Scope:** games first. Discord bots, voice servers, and generic Node/Python apps officially supported via eggs. Not a general app platform. | Communities run bots and voice alongside game servers, and eggs make it nearly free. General app hosting is Coolify/Dokploy's market. |
| 4 | **Names:** Raptor · **Panel** + **Wings** · CLI `raptor` | Pterodactyl-style naming. Wings is kept despite Pterodactyl's Wings, with full namespacing so they never collide on a box (#26). |
| 5 | **Domains:** `raptorpanel.net` (Panel, API, installer, node connections; Cloudflare-proxied); `raptornodes.net` (DNS-only: node hostnames `n-<short-id>.raptornodes.net` and player subdomains like `smp.raptornodes.net`) (updated by #71, #80) | Keeps node infrastructure and player-facing names off the Panel's domain. Player subdomains can't start with `n-`, so they never collide with node hostnames. |
| 6 | **License:** AGPL-3.0 for everything | Fully open source. Competitors are acceptable; forks must publish their changes. |
| 7 | **Contributions:** DCO, no CLA | Less friction, more contributor trust. Relicensing rights aren't needed because revenue comes from hosting, not licenses. |
| 8 | **Panel is SaaS-only.** No self-hosting support or concessions in the stack. | Keeps the codebase to one deployment target. |
| 9 | **Languages:** Go (all backend + Wings), TypeScript + React (web) | Go: single static binaries, strong concurrency, first-class Docker/containerd libraries. |
| 10 | **Contracts:** protobuf + Connect-RPC | One source of truth for Go and TS types. |
| 11 | **Panel:** one Go binary, one process role (`serve api`, which also holds node connections); Postgres only (River jobs, LISTEN/NOTIFY) (updated by #72) | Fewest moving parts. Deploys drop node connections briefly; Wings reconnects with jitter and servers are never affected. |
| 12 | **Hosting:** two servers (primary + Postgres streaming replica), Docker Compose, WAL archive in a different location. Provider intentionally not fixed in the docs. | Simple to run. Replica because Postgres is the Panel's single point of failure. Provider may change. |
| 13 | **Auth:** ~~WorkOS~~ built into the Panel, passwordless (superseded by #76) | |
| 14 | **Billing:** Polar (merchant of record). **$12/month for every enrolled node, regardless of status**; per-unit quantity subscription, prorated daily. First node free for one month, once per org, card required. Hosted backups $0.02/GB-month. | Polar handles global VAT and sales tax. Bills only on things Raptor can verify. Card-up-front trial blocks re-trial abuse. |
| 15 | **Non-payment never stops servers.** The Panel goes read-only for unpaid nodes. | Trust. The hardware is the owner's. |
| 16 | **Onboarding:** one command; join token; keys generated on the node; node proves itself by signing challenges (updated by #72) | The core UX promise. |
| 17 | **Wings dials out** and holds one connection; Panel is an RPC client over it (transport: #72) | No inbound management port, works behind NAT, one connection per node. |
| 18 | **Wings is local-first** and the source of truth for servers, schedules, backups, jobs, files | Servers survive Panel outages. |
| 19 | **Single writer:** the Panel sends commands; Wings owns state; the Panel keeps a disposable read-only mirror | No merge conflicts. The mirror keeps the UI fast and makes dead-box recovery possible. |
| 20 | **CLI scope:** keep servers running (status, power, console, logs, backups, doctor). No config changes. | Config only comes from the Panel (#19). Smaller API surface. |
| 21 | **No standalone Wings product.** Wings must be linked to be configured. | Follows from #20. Avoids a second product mode to test. |
| 22 | **Container runtime:** Docker behind a `Runtime` interface; `live-restore`, `userland-proxy: false`, `local` log driver, package held | Egg compatibility requires Docker images. Settings chosen for uptime and UDP performance. |
| 23 | **Docker firewall:** leave Docker's iptables on; Wings publishes only allocated ports; own rules in a `RAPTOR` chain (where the rules live: superseded by #56) | Disabling Docker's iptables would break networking for other containers on the box. |
| 24 | **Disk quotas:** XFS project quotas; XFS loop image (preallocated, direct I/O) on non-XFS hosts; soft limits only on opt-out | Kernel-enforced, zero overhead, instant usage readout. |
| 25 | **Eggs:** Pterodactyl (`PTDL_v1/v2`) and Pelican formats run natively; Raptor extras under `x-raptor`; Pterodactyl Wings' runtime behavior is the spec | Instant catalog. Extensions don't break other panels. |
| 26 | **Coexistence:** every on-box resource namespaced; labels `raptor.wings.*`; Wings never mentions the Panel's name or domain in code | Runs alongside Pterodactyl's Wings. Wings stays a cleanly separated program. |
| 27 | **Backups:** Kopia; on by default; Panel-held per-node key by default, owner-held optional | restic can't be embedded as a library. Panel-held key means backups survive a dead box. |
| 28 | **Files:** ~~small ops via tunnel; large transfers direct to the node over HTTPS~~ superseded by #73 | |
| 29 | **SFTP during Panel outage:** Wings caches users' SSH public keys and permissions; no password caching | Public keys aren't secrets. |
| 30 | **Support:** consent-based, scoped (3 levels), time-limited, audited; no shell for staff; `doctor --bundle` only as the offline fallback | Live access for connected nodes; bundle covers nodes that can't connect. |
| 31 | **Launch OS:** Debian 12, Debian 13, Ubuntu 24.04; amd64 + arm64 | Keeps the test matrix manageable. Add versions on demand. |
| 32 | **Certified games:** Minecraft family, Rust, and selected anonymous-SteamCMD games; x86-only games hidden on arm64 (Hytale moved to community, #100) | See [EGGS.md](EGGS.md). |
| 33 | **Beginner features in v1:** connection test, free subdomains, safe defaults, security warnings (never automatic changes), provider guides | The audience isn't Linux experts. |
| 34 | **CPU limits default to weight, not hard CFS quotas** | Hard quotas cause tick lag in game servers. |
| 35 | **Wings updates:** signed, staged, automatic rollback | A bad release must not strand nodes. |
| 36 | **Release signing:** minisign (Ed25519) over `checksums.txt`. CI (GoReleaser) builds a **draft** release; the maintainer signs locally with the offline key (`task release:sign`) and publishes. The install script is generated per release with the binary's SHA-256 embedded; the `raptor` binary verifies later updates (`checksums.txt.minisig`, then SHA-256) with an embedded public key. | Simple for single binaries. The private key never touches CI. Avoids needing a verifier installed on a fresh box. |
| 37 | **Node ports:** SFTP 2022 (only when enabled), falling back to the first free port in 2022–2099. The Panel always shows the real port. (HTTPS file port removed by #73.) | Coexists with Pterodactyl (which uses 2022) without manual setup. |
| 38 | **No spike phase.** Riskiest assumptions (egg runtime, XFS quotas, node connection) are validated as the first tasks of the phase that needs them. | Owner's call. The first task in each phase is a validation gate instead. |
| 39 | **Dev tools pinned in `tools/go.mod`** and run via `go tool -modfile=tools/go.mod` (buf, sqlc, protoc plugins, golangci-lint, govulncheck, go-licenses). gitleaks runs from its pinned Docker image. | Same versions locally and in CI, nothing to install globally, and tool dependencies stay out of the shipped binaries. gitleaks' dependencies conflict with golangci-lint's in a shared module. |
| 40 | **Biome** for web lint + format (not ESLint/Prettier) | The web app uses TypeScript 7 (native compiler), which typescript-eslint doesn't support. Biome is one fast tool with no TypeScript dependency. |
| 41 | **Generated code is committed** (Go protobuf, sqlc, TS protobuf, route tree); CI fails if it's stale | The project builds with plain `go build` / `pnpm build`, and generated changes show up in review. |
| 42 | **Taskfile is the single entry point** for dev and CI (`task check` = everything CI runs) | CI and local runs can't drift apart. |
| 43 | **Wings dev VM:** Lima, Debian 12, Docker CE from Docker's repository | Wings is Linux-only. Docker CE matches what the installer will use; Debian's `docker.io` is years behind. |
| 44 | **Install containers are isolated as untrusted code:** separate short-lived container, only the server dir (rw) and script (ro) mounted, never privileged, limits + 2h default timeout, own network with outbound-internet-only access (host, private ranges, other servers, and cloud metadata blocked), symlink-safe `lchown` afterwards | Egg install scripts run as root with internet access and come from third parties. Pterodactyl-compatible behavior is kept (root, `/mnt/server`, reinstall over existing files); the isolation is added around it. |
| 45 | **Servers store an egg snapshot**, not a live reference | Catalog updates must never silently change a running server. Updating the egg is an explicit action. |
| 46 | **Wings, not Docker, restarts servers** (restart policy `no`, `desired_state` reconciled on start) | Wings must verify the quota volume is mounted before starting anything; Docker's restart policy would bypass that. |
| 47 | **Graceful stop on host shutdown** via `raptor-shutdown.service`, plus Docker `shutdown-timeout: 90` | Docker's default short stop timeout can corrupt worlds that are still saving. |
| 48 | **Crash policy:** exit 0 counts as a crash by default (Pterodactyl-compatible); restart immediately after the 1st crash and after 10 s after the 2nd; the 3rd in 10 min = crash loop, stop and notify | Predictable, matches Pterodactyl, and avoids infinite restart loops. (Originally listed delays of 0/10/30/60 s, but with a loop at 3 crashes the 30 s and 60 s delays could never happen.) |
| 49 | **Console:** always drained, 1,000-line ring buffer, 1,000 lines/s streamed to viewers with a suppression marker, never kill a server for spam | A chatty or broken server can't stall Wings, browsers, or itself. |
| 50 | **Deleting a server keeps offsite backups** (orphaned, 30-day expiry for hosted); local backups are deleted | Deletion is irreversible; offsite backups are the only way back. |
| 51 | **`config.yml` holds only static box settings**, strict parsing; everything else lives in SQLite from the Panel | One source of truth for server config; typos in the file fail loudly. |
| 52 | **Install success = no Docker error and no timeout**, not the script's exit code (Pterodactyl-compatible); a non-zero exit is recorded and shown as a warning | Many community install scripts end with a harmless failing command. Failing them would break working eggs. |
| 53 | **Eggs are tested for real:** certified eggs are installed and run with their unmodified images (since 1.8 by the conformance suite, #102, which replaced `task e2e:eggs` and the "E2E eggs" workflow) | Egg compatibility can only be proven by running eggs. Rust's ~10 GB download is too slow for every PR. |
| 54 | **Local API methods are added only when implemented** (starting with `GetStatus`), not declared up front | No placeholder RPCs, and `buf breaking` never blocks designing a method properly when its feature is built. |
| 55 | **Squash merges only; `main` requires signed commits** | GitHub signs squash merges with its own key, but rebase merges recreate commits without any signature (PR #4's five commits landed unverified that way). |
| 56 | **Firewall rules live in Wings' own nftables table** (`inet raptor`, base chains at priority `filter - 1`), not a `RAPTOR` chain jumped to from `DOCKER-USER` | A drop in any table is final, so the rules hold regardless of Docker's. Docker never flushes a table it doesn't own, `DOCKER-USER` doesn't exist with Docker's nftables backend, and mixing native nft rules into iptables-nft's tables is unsupported. The table is replaced atomically and reapplied if removed. |
| 57 | **Network subnets are picked by Wings when the network is created**, avoiding host interfaces, kernel routes, and other Docker networks; config can pin them | The installer can't know about Docker networks created later, and a collision with a home LAN or VPN breaks the box's connectivity. Existing networks are never changed. |
| 58 | **Install containers may reach the host's DNS resolvers on port 53**, even in private ranges | Docker's embedded DNS forwards from the container's namespace, and home boxes resolve through their router. Blocking it would break every install. Only port 53, only the configured resolvers. |
| 59 | **`raptor.slice` memory ceiling = RAM − max(1 GiB, 10%) (at most 4 GiB reserved)**, set at runtime with `systemctl set-property --runtime` on every Wings start | Servers together can't starve the OS, Docker, or Wings. Runtime properties follow RAM changes and leave no files behind. |
| 60 | **`127.0.0.1` allocations are bound to the `raptor0` gateway**; `SERVER_IP` is unchanged | Pterodactyl's behavior (it rewrites the binding, not the variable). Reachable from the host and other servers, not the internet. |
| 61 | **Variable rules follow Laravel's semantics exactly** (empty = null, type-dependent sizes, string `boolean` = `0`/`1`), and unknown rules or PCRE-only patterns are skipped and linted, not failed | Eggs were written and tested against Laravel; any difference makes working eggs fail or broken values pass. Checked against 606 community eggs. Skipping unknown rules keeps eggs usable; the lint surfaces them for the catalog. |
| 62 | **Config parsers edit files in place** instead of re-serializing them like Pterodactyl's Wings | Owners hand-edit these files. Re-serializing loses YAML comments and key order and collapses duplicate INI keys (Unreal configs). In-place edits change only what the egg targets. |
| 63 | **Where Pterodactyl's config parsers are broken, Raptor does what the egg intends** (`list[0].key`, exact `if_value`, multiple `*`; since the diff test, only multiple `*` and unresolved placeholders in the text parser still differ from current Pterodactyl, #108) | These cases do nothing or corrupt files in Pterodactyl, so no working egg depends on the broken behavior, and the affected eggs (e.g. BungeeCord) start working. |
| 64 | **Placeholders are resolved by Wings**, for both Pterodactyl (`server.build.*`) and Pelican (`server.allocations.*`, `server.environment.*`) eggs | Wings is the source of truth for servers and must work without the Panel. |
| 65 | **Architecture is checked against the registry's manifest list before any download** | An x86-only egg on an ARM box should fail in a second with a clear message, not after a 10 GB SteamCMD download with `exec format error`. |
| 66 | **Console output comes from Docker's log stream; stdin is a separate stdin-only attach** | Nothing has to keep reading an attach stream, so a stalled reader can never block the game's output, and timestamped lines let Wings resume exactly (no gaps or duplicates) after Wings or Docker restarts. |
| 67 | **OOM kills are detected from the kernel's `oom_kill` counter on `raptor.slice`**, not only Docker's flag | Docker 29 on cgroup v2 doesn't report OOM kills at all (verified: kernel log shows the kill, `OOMKilled=false`, no event). Owners most need to know when a server ran out of memory. |
| 68 | **Container scopes are stopped after `raptor-shutdown.service`** with a `docker-.scope.d` prefix drop-in (`Before=`; see #87) | With the systemd cgroup driver, systemd stops container scopes itself at shutdown, in parallel, with a plain SIGTERM, which bypasses graceful stops. The drop-in only orders; it never starts anything. |
| 69 | **Each start creates a fresh container** | Configuration changes (allocations, limits, image, variables) apply on the next start with no diffing, as in Pterodactyl. |
| 70 | **The last runtime state is stored** (`last_state`) | After a Wings restart, a server whose "done" line scrolled out of the console history must still be adopted as running, not stuck at starting. |
| 71 | **Node hostnames are `n-<short-id>.raptornodes.net`**, DNS-only, random and never reused, kept current from the IP Wings reports (dynamic DNS) | Gives every owner a hostname for players and SFTP, including home boxes with changing IPs. The `n-` prefix keeps player subdomains from colliding; never reusing IDs keeps old caches from pointing at someone else's box. |
| 72 | **The node connection is a WebSocket through Cloudflare into `panel serve api`**, with yamux inside. Nodes prove themselves by signing a challenge with their own key; Wings verifies the Panel with a pinned signing key. Always reconnecting (ping every 30 s, jittered backoff), never required. No separate tunnel process, no mTLS, no `tunnel.raptorpanel.net`. | The Panel is behind the Cloudflare proxy, which only carries HTTP(S)/WebSockets and terminates TLS, so raw mTLS can't pass through. One process is simpler; deploys briefly drop nodes, which reconnect on their own. Idle cost is one ping per 30 s. |
| 73 | **Wings runs no HTTP server.** Web file operations go through the Panel (chunks under 100 MB, resumable, 1 GB per-file cap, on a separate short-lived outbound connection); bigger files use SFTP. SFTP is off by default. Nodes need no TLS certificates. | Fewer open ports and no certificate machinery on nodes. The cap bounds Panel bandwidth and respects Cloudflare's limits; SFTP is direct and free. |
| 74 | **Cloudflare can read Panel traffic** (console, commands, web file transfers); accepted for v1 and disclosed in the privacy policy | Re-encrypting inside the WebSocket is real extra work. SFTP is the private path for files. |
| 75 | **`raptornodes.net` needs DNS capacity sized for launch** (a Cloudflare plan or provider with enough records per zone) | One record per node plus two per player subdomain exceeds Free-plan zone limits quickly. |
| 76 | **Auth is built into the Go Panel, passwordless:** passkeys (preferred), OAuth (Google, Discord, GitHub), email codes + links, TOTP 2FA with recovery codes; Panel-issued sessions; re-auth for sensitive account actions (node actions that destroy data, change code, or change access are passkey-signed instead, #77). No WorkOS or other auth vendor. | Owner's call: one stack, no auth vendor, no vendor outage blocking logins, and fits the open-source project. Passwordless removes the hardest part of running auth yourself (storing and resetting passwords). Passkeys are the strongest option available. |
| 77 | **Dangerous actions are signed by the user's passkey over the exact command and verified by Wings** against keys pinned on the node (enrollment pin with fingerprint comparison, additions signed by trusted keys, owner-signed delegations for sub-users, local `raptor keys reset` for recovery). On by default; only root on the box can change it. | Makes a full Panel compromise unable to destroy servers, backdoor them through eggs or images, or add access without a real person's passkey per action. Costs ~0.1 ms on the node and one tap for the user, replacing the re-auth prompt those actions already had. Designed into the Phase 1.5 command envelope because adding it after nodes ship would be a protocol migration. |
| 78 | **The web app is hosted separately from the API**, with separate deploy credentials, a strict CSP, and reproducible builds with published hashes | The web app asks passkeys to sign, and browsers don't show what's being signed. Compromising the API or database must not change the code users run. |
| 79 | **Signed actions require a passkey**; TOTP protects sign-in but can't authorize them | Wings can verify a passkey signature on its own; it can't verify a TOTP code without holding the shared secret. |
| 80 | **Hostnames:** `raptorpanel.net` is the landing page and waitlist (`www` redirects to it); `app.raptorpanel.net` the web app; `api.raptorpanel.net` the API and node connections; `docs.raptorpanel.net` the docs; `get.raptorpanel.net` the install script; `status.raptorpanel.net` the status page (hosted and resolved outside Cloudflare); a separate subdomain for sending transactional email. `raptornodes.net` hosts nothing of ours and its apex redirects to `raptorpanel.net`. Replaces the Panel on the apex with the API under `/api`. | The landing page and the Panel can't both own the apex, and marketing pages (analytics, forms, frequent deploys) shouldn't share an origin with the app that asks passkeys to sign. Each site deploys on its own. |
| 81 | **The API has its own origin, `api.raptorpanel.net`**, not `/api` on the web app's origin. CORS allows exactly `https://app.raptorpanel.net` with credentials, with preflights cached. Wings connects to `wss://api.raptorpanel.net/nodes/connect`. | Whoever serves a response controls its headers. On the app's origin, a compromised API could serve an HTML page that asks passkeys to sign, or register a service worker (`Service-Worker-Allowed: /`) that replaces the app for good, undoing #78. On its own origin it can't touch the app or use the app's RP ID. A dedicated hostname for nodes also lets the web app's hostname change without reconfiguring every node. |
| 82 | **The passkey RP ID is `app.raptorpanel.net`**, not `raptorpanel.net` | With the registrable domain as RP ID, any `*.raptorpanel.net` page (landing, docs, status) could ask users' passkeys for signatures, so compromising the landing page would be enough to phish signed commands. Passkeys are bound to their RP ID forever, so this is fixed before the first passkey is registered. |
| 83 | **Sessions are a host-only `__Host-` cookie on `api.raptorpanel.net`** (`Secure`, `HttpOnly`, `SameSite=Strict`, no `Domain`), and the API rejects browser requests whose `Origin` isn't `https://app.raptorpanel.net` | Every `*.raptorpanel.net` site is same-site, so `SameSite` doesn't stop a compromised sibling from sending credentialed requests, and siblings can set cookies on the parent domain. The `__Host-` prefix blocks cookie tossing and session fixation; the `Origin` check blocks cross-subdomain requests. |
| 84 | **Frontends:** the web app stays a Vite + TanStack Router SPA (`web/`); the landing page is **Astro** (`site/`); the docs site is **Astro Starlight** (`docs-site/`, built once the installer exists). Not a single TanStack Start app. The web app loads no third-party scripts; analytics live only on the landing page. | Start is built around server rendering, which puts a server in front of the code passkeys trust (#78). One app would also mean one origin, one CSP, and one release cycle for marketing and the Panel. Astro ships static pages with almost no JS, and its islands can reuse React components when needed. |
| 85 | **`raptornodes.net` goes on the Public Suffix List** before launch | Let's Encrypt limits certificates per registered domain (about 50 a week), so owners getting certificates for their subdomains (web maps, dashboards) would otherwise share one limit. It also stops one subdomain from setting cookies for the others and contains the reputation damage from an abusive subdomain. Hard to reverse, so it's done before user subdomains exist. |
| 86 | **The accounts that control the domains are part of the trust boundary:** hardware-key 2FA (no SMS recovery) on the registrar and Cloudflare, registrar lock, scoped API tokens (the web app's deploy token can only deploy it; the API servers hold no Cloudflare token). Whether the web app is hosted under a separate account or provider from DNS and the proxy is decided before launch. | Whoever controls DNS or the static host controls the code users run, which bypasses #78 entirely. |
| 87 | **The scope drop-in is `Before=raptor-shutdown.service`, and the reboot test checks the reboot's own shutdown.** Correction: the first version used `After=`, which systemd applies in reverse at shutdown, so it killed game containers *before* the graceful stop, and the reboot check passed anyway because it matched an earlier manual stop in the same boot. | Found while testing Phase 1.5. The fixed check fails with the old drop-in and passes with the new one (both verified with real reboots). |
| 88 | **Installs are durable, resumable jobs**; interruptions count as attempts (3 max); install output is the job log | Wings restarts and updates must not fail installs. Re-running an install script over the files is how Pterodactyl reinstalls anyway. |
| 89 | **Creating a server is a signed action** | It chooses the egg, and so the install script and image that run. Same reasoning as changing the egg. |
| 90 | **Event retention: acknowledged 7 days, unacknowledged at most the newest 100,000**; readers behind that rebuild from a snapshot | Bounded storage on nodes that never reach a Panel, without losing anything a connected Panel needs. |
| 91 | **The Panel grant is bound to one command ID** and the Panel's key is required for every command | A captured grant can't authorize anything else; an unlinked node accepts no remote commands at all. |
| 92 | **The XFS loop volume (tier 2) stays the default on ext4 boxes**, even though fsync'd writes run at about half native speed; the installer explains the cost and offers a data disk (tier 1, native speed) or soft limits (tier 3). Direct I/O stays on. | Owner's call, after the 1.6 gate measured it on a real Linux runner: everything else is at native speed, and ~1,000–2,900 fsync'd saves per second is far more than game servers do. A soft limit can be overrun between scans, so it doesn't protect the other servers on a box. Direct I/O off was slower for fsync (41% vs 48%). The gate's "within ~10% of native" bar is waived for fsync only. |
| 93 | **Every Raptor container gets a seccomp profile that refuses `FS_IOC_FSSETXATTR`**: Docker's default profile with `ioctl` allowed per command instead of unconditionally. Written as allow-only rules. | A file's owner can move it to another quota project without any capability and escape its disk limit; the gate did it from a server container (uid 988). libseccomp lets a matching allow win over a matching deny, so a deny rule wouldn't work; allow-only rules also refuse values with extra high bits (the kernel truncates them to the blocked command). |
| 94 | **The volume's mount unit uses `DefaultDependencies=no`** with explicit ordering (after local filesystems, before Docker and Wings, unmounted after them), and is wanted by `multi-user.target` | With default dependencies it formed an ordering cycle that systemd resolved by silently skipping the mount at every boot, which the gate caught with a real reboot. Not `local-fs.target`: a broken volume must not send a remote box to emergency mode; Wings refuses to start servers instead. |
| 95 | **Quota tests run in CI on every PR** (a real XFS loop volume on the runner), and the reboot in `task e2e:quotas` | The escape and the boot-time mount were both real bugs that only a real kernel and a real reboot showed. |
| 96 | **On the local socket, the `raptor` group can look and root can act**: status, `ps`, console output, and logs for the group; power actions and console commands only for root | The group is for people who should see what's happening (support, monitoring) without being able to stop servers. Anyone who should act already has sudo, and the Panel's own `console.write` rule for local use was already "root". |
| 97 | **Short server IDs are the last 8 characters of the ID**, not the first | IDs are UUIDv7: the first characters are a timestamp, so servers created within a minute of each other share them. The end is random. |
| 98 | **Power actions are recorded as `server.power` events with who asked**, from the Panel and the CLI alike, before the action runs | Stop can take minutes; the audit log should say who asked for it even if Wings restarts meanwhile. |
| 99 | **The dev VM uses a real quota volume** (`raptor storage setup` in `task wings:vm:install`) | Development should run the production path. It found that `storage setup` failed on a box where Wings had never run. |
| 100 | **Hytale isn't certified**; it's a community egg | Its official server image signs in to a Hytale account (OAuth device flow) before downloading, so it can't be tested unattended. Owner's call over storing a game account token in CI. Owners still run it with their own account. |
| 101 | **The built-in catalog is unmodified upstream eggs plus a `raptor.yaml` each** (source commit, license, certified, arch, test settings), embedded by a Go package | Updating an egg means replacing a file, and diffs against upstream stay empty. Raptor's data lives beside the egg instead of inside it. |
| 102 | **Conformance runs in tiers**: fast eggs on PRs that touch eggs or the code that runs them, and nightly, on amd64 and arm64; big SteamCMD games weekly on amd64; CS2 by hand | Owner's call. Minecraft-family eggs take minutes; Steam games take up to an hour and tens of GB, and CS2 doesn't fit a standard runner's disk and needs a Steam login token. |
| 103 | **Wings says when a stop had to kill the server** (`didn't stop within …; killed`) | Owners should know a stop wasn't clean (possible data loss), and the conformance suite fails an egg whose stop doesn't work. |
| 104 | **An empty variable value fails only `required` and `filled`** (Pelican's behavior), not every type rule (Pterodactyl's) | Found by importing community eggs: Pelican-maintained eggs rely on it (SpongeVanilla's default config was rejected). Pelican's behavior accepts a superset of Pterodactyl's, so no working egg breaks. Replaces the earlier "empty is null" rule. |
| 105 | **The catalog only ships eggs that pass the conformance suite**; upstream eggs that are broken are left out, listed with the reason, and replaced | A catalog entry is a promise that it works. Of 64 community eggs tried, 18 didn't work (dead download APIs, renamed binaries, done strings that no longer match, servers that crash under Wine). |
| 106 | **Community eggs' CI jobs don't fail the build** (they report in the job summary); certified eggs' do | An upstream egg breaking shouldn't block Raptor's PRs, but it must be visible. |
| 107 | **Every server gets a read-only `/etc/machine-id`**: the server ID without dashes, like Pterodactyl | Found by the diff test. Hytale encrypts its tokens with it, and matching Pterodactyl keeps a server's machine-id the same when it moves over. |
